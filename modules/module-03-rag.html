A

Foundations

What RAG is, the two pipelines every RAG system has, and the decision that frames the whole module: retrieve, fine-tune, or just use a big context window?

What is RAG, and why is it important?

Q · What is Retrieval-Augmented Generation, and why is it important?

RAG augments an LLM's generation with relevant information retrieved at query time from an external knowledge source. Instead of relying only on what's baked into the model's frozen weights (parametric memory), you fetch the right documents and put them in the context so the model answers from them. It's "open-book exam" instead of "closed-book."

Why it matters — RAG solves the four core weaknesses of a bare LLM:

  • Hallucination → grounding answers in retrieved evidence dramatically reduces made-up facts.
  • Stale knowledge → the model's training cutoff doesn't matter; update the knowledge base, not the weights.
  • No private/domain data → the model can answer about your internal docs it never saw in training.
  • No attribution → because answers come from specific sources, you can cite them (trust + auditability).
Say this in the interview

"RAG turns a closed-book model into an open-book one. It's the cheapest, fastest, most auditable way to give an LLM current, private, and citable knowledge — without the cost and staleness of retraining. That's why it's the default architecture for enterprise LLM apps."

Architecture & key components of a RAG pipeline

Q · Explain the architecture of a basic RAG system and its key components.

Every RAG system is two pipelines: an offline indexing pipeline (build the searchable knowledge base) and an online query pipeline (retrieve + generate per request). Drawing both — and knowing they're separate — is the answer interviewers want.

Interview framing

"Retrieve → Augment → Generate is the loop, but 80% of real quality comes from the offline indexing choices — chunking, embeddings, metadata — plus reranking. If retrieval is bad, no prompt or model can save the answer. Garbage retrieved, garbage generated."

RAG vs fine-tuning — when to use each

Q · Compare RAG vs fine-tuning. When would you use each?

The classic trap is treating these as competitors. They solve different problems: RAG changes what the model knows (knowledge injection); fine-tuning changes how the model behaves (skill, format, tone, domain style). The best systems often use both.

The decision heuristic to say out loud

"Knowledge problem → RAG. Behavior problem → fine-tune. If the model doesn't know something, retrieve it. If it doesn't know how to act — wrong format, wrong tone, can't follow a niche task — fine-tune. Start with prompt engineering, add RAG for knowledge, and only fine-tune when prompt+RAG can't hit the behavior bar, because it's the most expensive and least flexible."

"Is RAG dead?" — the long-context debate

Q · With million-token context windows, is RAG obsolete? (a 2026 curveball)

This is the hot 2026 question and a fantastic one to nail because most candidates give a naive answer. The reality: naive RAG is dead; sophisticated RAG is thriving. Million-token windows (Gemini, Claude) tempt you to just dump everything in the prompt — but that fails for real corpora because of context rot (accuracy degrades as irrelevant tokens fill the window), cost (paying to process huge context every call), freshness, and — critically for you — access control and citations.

The nuanced 2026 answer that wins

"It's not binary. Long context wins for small (<200k tokens), stable corpora needing whole-document reasoning. RAG wins when the relevant material is a tiny fraction of a large, changing, or access-controlled corpus — you can't fit 10M enterprise docs in a window, and even if you could, context rot kills accuracy. The 2026 winning pattern is hybrid: retrieve to narrow, then use long context to reason across what you retrieved. Prompt caching also shifted the economics. It's a context-engineering decision, not a tool war."

RAGGuard hook

Access control is a decisive RAG advantage you should raise unprompted: you cannot enforce per-user document permissions by stuffing everything into a context window — the model would see documents the user isn't allowed to. RAG lets you filter before retrieval. This is exactly what RAGGuard exists to do (see §G).

B

Indexing & Chunking

Where most RAG quality is won or lost. If you chunk badly, retrieval never recovers — so interviewers probe this hard to see if you've actually built a system.

Chunking strategies & choosing chunk size

Q · What are chunking strategies, and how do you choose the right chunk size?

Chunking splits documents into pieces small enough to embed and retrieve precisely, but large enough to carry self-contained meaning. It's a fundamental tension: too small → chunks lose context and you retrieve fragments that don't answer the question; too large → embeddings become "diluted" averages of many topics, hurting retrieval precision, and you waste context tokens.

Choosing size is empirical, not a magic number — it depends on document type and query type. Dense technical docs and short factual queries want smaller chunks (~256 tokens); narrative or reasoning content wants larger (~512–1024). Add overlap (e.g. 10–20%) so a sentence split across a boundary still appears whole in one chunk.

Say this in the interview

"I don't guess chunk size — I treat it as a hyperparameter and tune it against a retrieval eval set. Start ~512 tokens with ~15% overlap as a baseline, then measure context precision/recall and adjust per document type. Chunk size is not a constant across a heterogeneous corpus."

Fixed-size vs recursive vs semantic chunking

Q · Compare fixed-size, semantic, and recursive chunking.

  • Fixed-size: split every N characters/tokens. Simple and fast, but blindly cuts through sentences and ideas. Fine as a baseline, rarely best.
  • Recursive (recommended default): split hierarchically — try paragraph breaks first, then sentences, then words — until chunks fit the size target. Respects natural boundaries with almost no extra cost. This is what most production systems use.
  • Semantic: embed sentences and place a boundary where consecutive-sentence similarity drops (a topic shift). Produces the most topic-coherent chunks but is compute-heavy (you embed during indexing to decide splits) and can be inconsistent.
Latest

Beyond these, know document-structure-aware chunking (split on markdown/HTML headings, code by function) and late chunking (embed the whole document first with a long-context embedder, then pool per-chunk — so each chunk's vector already carries document context). These beat naive splitting on structured content.

Parent-child (small-to-big) chunking

Q · What is parent-child chunking, and how does it improve retrieval?

Parent-child resolves the size tension directly: embed and search on small "child" chunks for precise matching, but feed the larger "parent" chunk to the LLM for full context. You get retrieval precision and generation context at once.

Why this impresses

Naming parent-child (a.k.a. "small-to-big" / auto-merging retrieval) shows you understand the precision-vs-context trade-off and a clean fix for it — a strong signal you've moved past tutorial RAG.

Contextual retrieval

Q · (2026 must-know, not in the base list) How do you stop chunks from losing document context?

A chunk like "The margin rose to 23%." is useless in isolation — whose margin, which quarter? Contextual retrieval (popularized by Anthropic) fixes this: before embedding each chunk, prepend a short LLM-generated blurb situating it in its document ("This chunk is from Acme's Q3 2025 10-K, discussing gross margin: The margin rose to 23%."). Both the embedding and a BM25 index are built on the contextualized chunk.

Latest — worth volunteering

Anthropic reported contextual retrieval cut failed retrievals by ~35%, and ~49% when combined with a reranker. It pairs perfectly with prompt caching (cache the doc, cheaply generate context for each chunk). Mentioning this unprompted signals you read primary sources, not just tutorials — exactly the RAG depth that separates you in an interview.

Structured data, tables & PDF parsing

Q · How do you handle tables/SQL in RAG? How do you fix PDF parsing with tables and layouts?

Tables & layout-heavy PDFs are where naive RAG breaks: a plain text extractor flattens a table into meaningless streams of numbers, destroying the row/column relationships. Fixes, in order of sophistication:

  • Layout-aware parsing: use tools that understand document layout (e.g. layout models / vision-based parsers) to extract tables as structured Markdown/HTML, preserving rows and columns.
  • Table summarization: generate a natural-language summary of each table, embed the summary for retrieval, but keep the original table to hand to the LLM (a parent-child pattern for tables).
  • Multimodal: for truly complex layouts, embed page images with a vision model and let a VLM read them (multimodal RAG — Module 11).

SQL / structured databases: don't embed rows — use Text-to-SQL. The LLM translates the question into a SQL query, runs it against the real database, and answers from the exact result. This is the correct pattern for precise, numeric, or aggregate questions ("total revenue by region in Q3") where semantic search over text would be hopeless. Many production systems are hybrid: route factual/aggregate questions to Text-to-SQL, semantic questions to vector RAG.

Say this in the interview

"I match the retrieval method to the data type: unstructured text → vector RAG; tables → layout-aware parsing + table summaries; structured DBs → Text-to-SQL. Forcing everything through one vector index is a classic reason RAG systems fail on numbers and tables."

Embeddings for Retrieval

The model that turns text into the vectors you search over. (Deep embedding theory is Module 6 — here's the RAG-practical view.)

Embedding models: text → vectors

Q · What are embedding models, and how do they convert text to vectors?

An embedding model maps a chunk of text to a dense vector (e.g. 768–3072 dims) positioned so that semantically similar text lands nearby in vector space. At query time you embed the question and find the nearest chunk vectors by cosine similarity — that's semantic search, and it's why a query and a relevant doc match even with zero shared keywords.

For RAG, these are typically bi-encoders: query and documents are embedded independently, so you can pre-compute all document vectors offline and just do fast nearest-neighbor lookup at query time. That independence is what makes them scalable — and also what makes them "lossy," which is the whole reason rerankers exist (§D).

Concrete example

Query "how do I reset my password" embeds close to a doc chunk titled "account recovery steps" despite no word overlap. That semantic bridge is RAG's core mechanism — and the reason keyword search alone (BM25) misses relevant docs, which is why we combine them (hybrid).

Choosing an embedding model for your RAG system

Q · How do you choose an embedding model for your RAG system?

Don't pick by leaderboard rank alone — choose on the axes that matter for your deployment:

AxisWhat to weigh
QualityStart from the MTEB benchmark for retrieval, but validate on your own data — leaderboards don't reflect your domain.
Domain fitLegal/medical/code jargon? A domain-tuned or code-specific embedder often beats a bigger general one.
DimensionalityHigher dims = better quality but more storage + slower search. Some models (Matryoshka) let you truncate dims to trade quality for cost.
Cost / hostingAPI (OpenAI text-embedding-3, Cohere, Voyage) = zero ops; open (BGE, E5, Nomic, Jina) = self-host, data stays in-house.
Context lengthMax tokens per chunk the model handles — matters for large-chunk / late-chunking strategies.
MultilingualNeed Hindi/Gujarati/etc.? Pick a multilingual embedder (BGE-M3, multilingual-E5) — English-only models tank on other scripts.
Say this in the interview

"I shortlist from MTEB, then run a bake-off on a labeled slice of my corpus measuring recall@k — the leaderboard winner often loses on domain data. I weigh dimensionality against storage/latency, and if data can't leave our infra I go open-weight and self-host. And crucially, both indexing and querying must use the same embedding model — a mismatch silently destroys search quality."

Trap: embedding drift

If you switch embedding models later, you must re-embed the entire corpus — old and new vectors live in incompatible spaces, so mixing them crashes search quality overnight. Plan migrations as a full re-index with a shadow/blue-green cutover, and version your embeddings. (This is a common troubleshooting question — see §J and Module 6.)

D

Retrieval — getting the right chunks

The heart of a modern RAG system. The 2026 production standard is a two-stage funnel: cast a wide net cheaply, then precisely rank. Master this section and you've covered the highest-ROI part of RAG.

Hybrid search & Reciprocal Rank Fusion

Q · What is hybrid search, and why is it better than pure vector search?

Pure vector (dense) search is great at meaning but weak at exact matches — product codes, error IDs, names, rare acronyms. Keyword search (BM25, sparse) is the opposite: precise on exact terms, blind to synonyms. Hybrid search runs both and fuses the results, capturing semantic similarity and exact-term precision.

Say this in the interview

"Hybrid search is close to a free lunch — dense for semantics, sparse/BM25 for exact terms, fused with RRF. It's the fix when vector search misses on names, IDs, or jargon. I'd default to hybrid for any real corpus." (This is also the answer to 'RAG fails on domain jargon' — hybrid + a domain embedder.)

Re-ranking — the highest-ROI upgrade

Q · What is re-ranking, and how does it improve RAG retrieval quality?

First-stage retrieval (bi-encoder + BM25) is fast but lossy — it compares independently-computed vectors, so it's approximate. A reranker (cross-encoder) takes the query and each candidate chunk together and scores their true relevance with full attention between them. It's far more accurate but too slow to run over the whole corpus — so you use it as a second stage on a small candidate set.

Say this in the interview

"Two-stage retrieval is the modern default: hybrid gets me ~100 candidates fast, a cross-encoder reranker cuts that to the 5–10 that actually answer the question. It directly fixes the 'high similarity score but irrelevant result' failure, and it lets the LLM see clean context instead of noise — which also cuts hallucination and cost."

Metadata filtering

Q · What is the role of metadata filtering in RAG?

Alongside each chunk's vector you store metadata: source, author, date, department, doc type, language — and, critically for you, access permissions / tenant ID. At query time you filter on metadata so vector search only runs over the allowed, relevant subset ("only 2025 finance docs," "only docs this user can see"). It sharpens relevance, cuts latency (smaller search space), and is the mechanism behind freshness and access control.

RAGGuard hook — pre-filter vs post-filter

There's a subtle, interview-critical distinction: pre-filtering (apply the metadata filter before the ANN search) vs post-filtering (search first, then drop disallowed results). For access control you must pre-filter — post-filtering can return zero results after dropping forbidden docs, and leaks information about what exists. This is a core RAGGuard design point; make sure you can explain it (full treatment in §G).

Query transformation — HyDE, decomposition, step-back

Q · What is query transformation in RAG (HyDE, query decomposition, step-back prompting)?

Users write short, messy, or ambiguous queries that don't embed well against full documents. Query transformation rewrites the query before retrieval to improve the match. Three techniques to name:

  • HyDE (Hypothetical Document Embeddings): ask the LLM to generate a fake ideal answer to the query, then embed that and search with it. A hypothetical answer sits closer in vector space to real answer-documents than the short question does — you're matching answer-to-answer instead of question-to-answer.
  • Query decomposition: break a complex multi-part question into sub-questions, retrieve for each, then combine — essential for multi-hop (below).
  • Step-back prompting: generate a more general "step-back" question first ("What is the refund policy?" from "Can I return shoes bought 40 days ago on sale?"), retrieve the broad principle, then answer the specific case.

Multi-hop questions & "lost in the middle"

Q · How do you handle multi-document/multi-hop questions? What is the "lost in the middle" problem in RAG?

Multi-hop questions require chaining facts across documents ("Who is the CEO of the company that acquired the startup Jane founded?"). Single-shot retrieval fails because no one chunk holds the whole chain. Fixes: query decomposition (break into hops, retrieve each), iterative/agentic retrieval (retrieve, reason, retrieve again based on what you learned — §E), or GraphRAG when relationships are the point (§E).

Lost in the middle (from Module 1): LLMs use info at the start and end of context far better than the middle. In RAG this dictates ordering — after reranking, place the strongest chunks at the head and tail, not buried in the center. And it's a hard argument against "just retrieve 50 chunks and let the model sort it out": more context isn't better, cleaner context is.

Say this in the interview

"I fight lost-in-the-middle two ways: retrieve fewer, better chunks via reranking, and order them strategically — best evidence first and last. For multi-hop I decompose the query or use an agentic retrieve-reason-retrieve loop rather than hoping one retrieval pass captures the whole chain."

E

Advanced RAG

The frontier patterns that define 2026 RAG. Knowing when each applies — not just what it is — is what gets you hired for senior/applied roles.

Agentic RAG

Q · Explain Agentic RAG.

Classic RAG is a fixed, one-shot pipeline: retrieve once, generate once. Agentic RAG puts an LLM agent in charge of retrieval as a tool it can call repeatedly, with reasoning between calls. The agent decides whether to retrieve, what to search for, can reformulate queries, retrieve from multiple sources, evaluate whether results are sufficient, and loop until it can answer.

Why it's the 2026 headline

Agentic RAG blends RAG with the agent patterns from Module 4 (ReAct, tool use). The trade-off to name: it's more capable but slower and pricier (multiple LLM + retrieval calls) and harder to evaluate — so you reserve it for genuinely complex queries and keep simple ones on a fast single-shot path (often via a router).

Self-RAG & Corrective RAG (CRAG)

Q · Explain Self-RAG. How does the model decide when to retrieve?

Self-RAG trains the model to self-regulate retrieval using special reflection tokens. Instead of always retrieving, the model first decides whether retrieval is even needed (skip it for "what's 2+2", trigger it for "our Q3 refund policy"). After retrieving, it critiques each passage for relevance, and critiques its own generation for whether it's actually supported by the evidence — regenerating if not.

Corrective RAG (CRAG) is a close relative worth naming: it grades retrieved docs and, if they're poor/irrelevant, falls back to web search or corrective action instead of generating from bad context. FLARE triggers retrieval mid-generation whenever the model's confidence drops. All three share one idea: retrieval should be adaptive and self-checking, not blind.

GraphRAG

Q · What is GraphRAG, and when would you use it over traditional RAG?

GraphRAG (Microsoft) builds a knowledge graph from your corpus — extracting entities and their relationships — instead of (or alongside) a flat vector index. Retrieval then traverses the graph, so the system can answer questions about connections and global structure that vector search fundamentally can't.

When to reach for it

"GraphRAG shines on relational and global questions — multi-hop chains, 'how do X and Y connect,' summarizing themes across a whole corpus — where vector search only sees local similarity. The cost is a heavier, pricier indexing step to build and maintain the graph, so I use it when relationships are central, not as a default. In practice, hybrid graph+vector is common."

F

Evaluation

You cannot improve a RAG system you can't measure, and "debug a bad RAG system" is a near-guaranteed interview question. This is where evaluation-driven candidates stand out.

Evaluating RAG — the triad & the metrics

Q · How do you evaluate a RAG system? Explain faithfulness, relevance, and context precision/recall.

The key insight: RAG has two subsystems that fail independently — retrieval and generation — so you evaluate them separately, then end-to-end. The RAG triad frames it:

Retrieval metrics (is the right context found?)

  • Context recall: of all the info needed to answer, how much did retrieval actually surface? Low recall → the answer can't be right; fix chunking/embeddings/hybrid.
  • Context precision: of what was retrieved, how much is actually relevant (and is it ranked high)? Low precision → noisy context; fix with reranking.

Generation metrics (is the answer good?)

  • Faithfulness (groundedness): is every claim in the answer supported by the retrieved context, with no invention? This is your primary anti-hallucination metric.
  • Answer relevance: does the answer actually address the user's question (not just recite context)?
How you measure these in 2026

Frameworks like RAGAS, TruLens, DeepEval, and Arize Phoenix compute these using LLM-as-a-judge (Module 9) — e.g. faithfulness by having a judge model check each answer sentence against the context. Build a golden eval set of query→ideal-context→ideal-answer, run it in CI on every change, and monitor the same metrics in production. "I run evaluation-driven RAG development with RAGAS-style faithfulness/precision/recall on a golden set in CI" is exactly the maturity signal recruiters want.

The debugging decision tree (say this)

"To debug a bad RAG system I first localize: is it a retrieval or a generation failure? If the right context wasn't retrieved → chunking, embeddings, hybrid, reranking. If the context was there but the answer is wrong → it's a generation/faithfulness problem → prompt, grounding instructions, or model. Splitting the pipeline before touching anything is the whole game."

G

Production & Security

Everything between a demo and a real system: attribution, scale, freshness, and — the part that is your project — enforcing who can see what.

Per-user access control & multi-tenancy RAGGuard

Q · Your RAG system needs per-user access control on internal documents. How do you implement it? (+ multi-tenant indexing)

This is your question — RAGGuard is a multi-tenant, permission-aware RAG system, so treat this as your set-piece answer. The core problem: in enterprise RAG, two users asking the same question must get answers built from different documents based on their permissions. A naive RAG system that searches the whole index and returns the top-k will happily leak a document the user was never allowed to see — a serious data breach, not a quality bug.

The non-negotiable principle: enforce permissions at retrieval time by pre-filtering, never rely on the LLM to withhold. The model must never even see unauthorized content — telling it "don't reveal restricted docs" is not security, it's a suggestion an injection can bypass.

Implementation choices (name the trade-offs)

  • Metadata-based pre-filtering (most common): tag every chunk with tenant_id, allowed_roles/groups, acl. At query time, resolve the user's permissions and pass them as a pre-filter so ANN search only runs over allowed vectors. Must be pre-filter, not post — post-filtering leaks existence and can empty your result set.
  • Namespace / index-per-tenant: physically isolate each tenant's data in its own namespace/collection. Strongest isolation (no cross-tenant leakage risk), simpler compliance — but more overhead and weaker for cross-tenant shared docs. Good for strict enterprise multi-tenancy.
  • Hybrid: namespace per tenant plus row-level ACL filtering within a tenant for per-user/per-group document permissions. This is the realistic RAGGuard architecture.
  • Keep ACLs fresh: permissions change (someone leaves a team). Sync document ACLs from the source system (SharePoint/Drive/Okta groups) into chunk metadata on a schedule or via events, so revoked access takes effect in retrieval quickly.
Your RAGGuard interview set-piece

"In RAGGuard I enforce permissions at retrieval, never at generation. Every chunk carries tenant and ACL metadata; I resolve the caller's identity to their groups and pre-filter the vector search so only authorized chunks are candidates — the LLM physically cannot see what the user can't. I use namespace isolation per tenant plus row-level ACL filtering within a tenant, sync ACLs from the source of truth so revocations propagate, and I test it with an authz eval set: for a given user, assert forbidden docs never appear in retrieved context. Pre-filter vs post-filter matters — post-filtering leaks document existence and can silently return empty."

Depth bonus

Raise the subtle risks that show real security thinking: (1) indirect prompt injection via a retrieved doc (Module 2) — an authorized-but-poisoned document can still hijack the agent, so combine access control with input guardrails; (2) data leakage through citations/logs — make sure your traces and cited snippets respect the same ACLs; (3) the embedding itself can memorize content, so isolation should extend to how you host embeddings. This turns "I filter by metadata" into a genuine security architecture.

Citations & source attribution

Q · How do you implement citation and source attribution in RAG?

Citations are what make RAG trustworthy and auditable — and, for you, tie into access control (never cite a source the user can't open). Implementation: carry a stable ID + metadata with every chunk through retrieval into the prompt; instruct the model to cite the specific chunk IDs it used (e.g. structured output with a sources field, or inline markers); then map IDs back to real document links in the UI. For higher rigor, run a post-hoc grounding check — verify each cited claim is actually supported by the cited chunk (an LLM-as-judge faithfulness pass), and flag or drop unsupported claims.

Say this in the interview

"I pass chunk IDs through the pipeline and have the model emit citations as structured output, then resolve them to source links. I also verify citations post-hoc for faithfulness so we don't show a citation that doesn't actually support the claim — a fake citation is worse than none."

Scaling to millions of docs & optimizing latency

Q · How do you scale a RAG system to millions of documents? How do you optimize RAG for latency in production?

Scale

At millions–billions of vectors, exact search is impossible — you rely on ANN (Approximate Nearest Neighbor) indexes like HNSW or IVF-PQ (Module 6) that trade a little recall for massive speed. Add sharding (partition the index across nodes), quantization (compress vectors to cut memory), and metadata pre-filtering to shrink the search space. Use a managed/distributed vector DB (Pinecone, Milvus, Weaviate, Qdrant, pgvector at smaller scale) built for this.

Latency

RAG adds a retrieval hop before generation, so latency levers include: ANN tuning (recall vs speed), caching (semantic cache for repeated/similar queries — Module 8; and prompt-cache the stable system prompt), limit reranking to a small candidate set, parallelize hybrid retrieval branches, stream the generation so time-to-first-token feels fast, and right-size k (fewer, reranked chunks = less context = faster generation and better quality).

Say this in the interview

"Scale is an ANN + sharding + quantization + pre-filtering problem; latency is a caching + streaming + 'retrieve fewer, better chunks' problem. Reranking down to 5 clean chunks helps both latency and quality — the biggest lever is usually not stuffing more context in."

Freshness, updates & versioning

Q · How do you handle document updates and maintain freshness? How do you version an evolving knowledge base?

Freshness: run an incremental indexing pipeline — on document create/update/delete, re-chunk and re-embed only the changed docs and upsert them (don't rebuild the whole index). Use content hashes or timestamps to detect changes, and propagate deletes (a stale/deleted doc lingering in the index is a common bug — the source of "RAG returns outdated answers"). Store a last_updated timestamp in metadata so you can prefer recent info and even filter by recency.

Versioning: tag chunks with a version / valid_from / valid_to so you can retrieve the version relevant to a query's time context, roll back a bad ingest, and reproduce what the system knew at a past moment (important for auditability and the "auditor asks why you answered X 6 months ago" scenario). Contradictory answers across doc versions are resolved by preferring the newest valid version and/or surfacing the conflict with sources.

The #1 freshness bug

Deletes that don't propagate. When a document is removed at the source, its chunks must be deleted from the vector index too — otherwise RAG keeps citing content that no longer exists. Wire deletes into the ingestion pipeline explicitly; don't assume re-embedding covers it.

The rapid-fire "your RAG does X — fix it" scenarios. Lead with retrieval-vs-generation triage, then the highest-leverage fix.

Rapid-fire fixes

SymptomFix (lead with this)
